- **[公式][実務] Claude Code v2.1.251 — 思考のみで終わったターンの後、会話が「text content blocks must be non-empty」エラーで固まる不具合を修正** — https://github.com/anthropics/claude-code/releases/tag/v2.1.251
  - **何が起きたか**: 8/28リリースのv2.1.251で、モデルがthinkingブロックのみを出力してテキストを返さなかったターンの後、以降の会話が「text content blocks must be non-empty」エラーで詰まり続ける不具合が修正された。
  - **なぜ注目されているか**: このエラー自体はGitHub Issueで#62150系統から#88536まで1年近く繰り返し報告されてきた古い問題で、多くが重複クローズされたまま解決していなかった。今回はそのうち「thinkingのみの空応答が原因で会話全体が壊れる」というパターンに限定して手が入った形。
  - **使いどころ**: `/loop`やroutineで長時間モデルに考えさせる運用をしていて、ある時点から会話が固まって動かなくなる事故に心当たりがあるなら、原因の一つが解消されたことになる。バージョンを上げておけば追加設定は不要。

- **[公式][実務][企画] Claude Code v2.1.251 — thinking無効時にeffort xhigh/maxを指定するとAPIエラーで落ちていた不具合を修正、自動的にhighへ降格** — https://github.com/anthropics/claude-code/releases/tag/v2.1.251
  - **何が起きたか**: 同v2.1.251で、thinkingが無効なモデルに対してeffort（xhigh/max）を指定すると「effort … is not supported when thinking is disabled」というAPIエラーで落ちていた不具合が修正され、その場合は自動的にeffortを`high`へ落として送るようになった。
  - **なぜ注目されているか**: この組み合わせによる失敗は8月だけでもissue #87126（Aug 16、サブエージェント起動時にeffort=xhighを渡して400エラー）や、8月頭のissue #83550（サブエージェントの起動経路がthinkingを強制的に無効化したままeffort=xhighを送り、Opusサブエージェントが0トークンで全滅していた）など複数報告されていた。効果的な設定のつもりが逆にサブエージェントを落としていた、という地味だが実害のある不具合だった。
  - **使いどころ**: 自作のサブエージェントやWorkflowでeffortをxhigh/maxに揃えて品質を上げようとしているなら、これまで気づかずサブエージェントが落ちていたケースが救済される。CDK/ECSレビュー用に高effortのレビュー専用サブエージェントを作る際も、この組み合わせで安心して使える。

- **[公式][実務] Claude Code v2.1.251 — 社内Claude apps gateway経由の利用で、自分の支出上限に対する使用率バーが`/usage`とステータスラインに追加** — https://code.claude.com/docs/en/claude-apps-gateway-spend-limits
  - **何が起きたか**: 8/28リリースのv2.1.251で、組織が自前運用する「Claude apps gateway」（Bedrock/Vertexなど共有のアップストリーム認証情報を1本にまとめ、開発者ごと・グループごとにUSD建ての支出上限を課す社内プロキシ）配下の利用時、開発者自身の支出上限に対する使用率を示す「Spend limit」バーが`/usage`に、`rate_limits.spend_limit`フィールドがステータスラインにそれぞれ追加された。
  - **なぜ注目されているか**: このgatewayはv2.1.225（8月上旬）から支出上限超過時に期間名・リセット時刻を含む具体的なエラーメッセージを返すようになり、75%・95%到達時の警告も追加されていた経緯がある。しかしそれまでは自分がどれだけ枠を使っているか能動的に確認する手段がなく、警告が出るまで気づけなかった。今回はその可視化が`/usage`とステータスラインという普段見る場所に追加された形。
  - **使いどころ**: マルチアカウントのAWS環境で、Bedrockの共有クレデンシャルを複数人・複数チームで使い回している、あるいは今後そうした社内ゲートウェイの導入を検討しているなら、開発者ごとの上限管理の選択肢として押さえておく価値がある。経験の浅いメンバーに使わせる際の「使いすぎ防止」の仕組みとしても使える。

- **[公式][実務][企画] Claude Code v2.1.248 — サブエージェントのfrontmatterに`experimental.cacheTtl`を追加、個別のサブエージェント単位でプロンプトキャッシュ保持時間を指定可能に** — https://code.claude.com/docs/en/sub-agents
  - **何が起きたか**: 8/27リリースのv2.1.248で、サブエージェント定義ファイルのfrontmatターに`experimental.cacheTtl`（`5m`または`1h`）が追加され、そのサブエージェントのリクエストだけプロンプトキャッシュの保持時間を個別指定できるようになった。
  - **なぜ注目されているか**: 8/26付ダイジェストで既報の`promptCacheTtl`/`subagentPromptCacheTtl`はsettings.json側で会話全体・サブエージェント全体に一律で効く設定だった。今回のfrontmatterの`experimental.cacheTtl`はそれとは別軸で、特定のサブエージェントファイル1つだけに効く、より細かい単位の指定になる（なお`1h`はClaudeサブスクリプションが使用クレジットを消費中は無視される）。
  - **使いどころ**: CDK/ECSレビュー用など複数のカスタムサブエージェントを使い分けているなら、長時間の調査を任せるサブエージェントの定義ファイルにだけ`experimental.cacheTtl: 1h`を書いて、他はデフォルトの5分のままにする、といった使い分けができる。自作サブエージェントを増やす作業のついでに設定しておくとよい。

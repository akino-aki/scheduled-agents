- **[公式][実務][企画] Claude Code v2.1.288（10/2）— `bypassPermissions`モードやBash全許可ルール下で、`rm`を`sh -c`/`bash -c`に文字列として渡すと「危険なrm操作」の確認が素通りしてしまう不具合を修正（issue #96300, 9/23報告）** — https://code.claude.com/docs/en/changelog
  - **何が起きたか**: v2.1.288で「Fixed a dangerous `rm`（`/`やホームディレクトリ対象など）が`bash -c`/`sh -c`スクリプト内にあると、bypassPermissionsモードやBashの許可ルール下で確認なしに実行されてしまう」不具合が修正された。issue #96300（9/23報告、Windows/Git Bash環境）では`rm -rf <cwd>`や`(rm -rf <cwd>)`、`echo $(rm -rf <cwd>)`は確認が働く一方、`sh -c "rm -rf <cwd>"`・`bash -c 'rm -rf <cwd>'`だけが素通りしてファイルが実際に削除される再現表が添えられていた。
  - **なぜ注目されているか**: 10/2付の本ダイジェストで報告したv2.1.287の3件の抜け穴修正（リダイレクト付き`rm`、MCPツール名`__proto__`、Bash全許可ルールでの保護ファイル書き込み）と同じ週に見つかった、別系統の4件目の抜け穴。原因は「危険操作チェックがサブシェル・ブレースグループ・コマンド置換は展開して見るが、`sh -c`/`bash -c`に渡された文字列の中身までは解析していなかった」という実装の抜け漏れで、プログラム名が`rm`ではなく`sh`/`bash`になるため検出をすり抜けていた。
  - **使いどころ**: auto modeや`Bash(*)`相当の全許可ルールで無人routineを組んでいるなら、v2.1.288への更新を優先する価値がある。「個別のルールは安全に見えても、コマンドの組み立て方（ラッパーで包む）次第で抜け道が生まれる」という視点は、IAMポリシーやCDKのセキュリティグループ設計レビューにもそのまま応用できる。

- **[公式][実務][企画] Claude Code v2.1.288（10/2）— PreToolUse/PermissionRequestフックが、マッチング失敗やツール入力のJSONシリアライズ失敗で静かにスキップされていた挙動を修正、以後はツール呼び出し自体をブロック** — https://code.claude.com/docs/en/changelog
  - **何が起きたか**: v2.1.288で「Fixed PreToolUse and PermissionRequest hooks being skipped when matching them failed or the tool's input could not be serialized to JSON; the call is now blocked」と明記された。従来はフックのマッチング処理自体が失敗したりツール入力がJSONにシリアライズできなかったりすると、フックが発火しないままツール呼び出しが通過していた。
  - **なぜ注目されているか**: 「設定したPreToolUse hookが実は発火していない」という失敗モードは根深く、issue #82323（マッチャーが登録されていないルールはエラーも出ず死んだコードになる）や、9/28付の本ダイジェストで報告した`matcher: "Skill"`の回帰（#96318）など、同種の報告が繰り返し上がっていた領域。今回はその中でも「マッチング処理そのものが失敗した場合」と「入力がJSON化できない場合」という2つの具体的な抜け道を名指しで塞ぎ、しかも失敗時の挙動を「スルーして通す」から「ブロックする」というフェイルセーフ側に変更した点が従来の個別修正と異なる。
  - **使いどころ**: skill/hook/routineを自作してauto modeで無人実行させているなら、v2.1.288への更新でフックの信頼性が一段上がる。ただし裏を返せば、これまで静かに素通りしていた呼び出しが今後は「ブロックされて止まる」側に倒れるので、更新直後は想定外の箇所でツール呼び出しが止まっていないか一度確認しておくとよい。

- **[公式][実務] Claude Code v2.1.288（10/2）— 無人セッション向けの未文書化機能`CLAUDE_CODE_RETRY_WATCHDOG`、長時間応答ストリームが失敗すると「数時間リトライし続ける」挙動を修正し3回失敗で諦めるように** — https://code.claude.com/docs/en/changelog
  - **何が起きたか**: v2.1.288で「Fixed unattended sessions (`CLAUDE_CODE_RETRY_WATCHDOG`) retrying for hours after a very long response stream failed; Claude Code now streams again, and gives up after three timeouts」と明記された。`CLAUDE_CODE_RETRY_WATCHDOG=1`は、CI等の無人セッションで429/529（過負荷エラー）を既定のリトライ上限を超えて延々とリトライし続ける機能。
  - **なぜ注目されているか**: この機能自体はissue #81330（7/26報告）で初めて存在が明らかになった未文書化機能で、報告者がv2.1.220のコードを解析して「通常のリトライは約2.5分で尽きてしまい、実際の過負荷障害（数十分単位）に対応できない」実態と合わせて指摘したものだった。しかし今回修正された問題は、その救済策であるはずのwatchdogモード自身が、長時間応答ストリームの失敗時には「数時間リトライし続けて終わらない」という別の無限待ち状態に陥りうるというもので、無人routineの信頼性に関わる同系統の問題が機能の内側にまだ残っていたことを示している。
  - **使いどころ**: CIやクラウドセッション、このダイジェストのような無人routineで長時間かかる処理（大きなコンテキストの要約や長い出力の生成）を組んでいるなら、v2.1.288への更新で「過負荷障害からの復旧狙いが、逆に終わらないリトライ地獄になる」リスクが下がる。`CLAUDE_CODE_RETRY_WATCHDOG=1`自体は依然ドキュメント未掲載の環境変数なので、使う場合は挙動の変更履歴をchangelogで追う必要がある。

- **[公式][実務] Claude Code v2.1.288（10/2）— `/code-review`に`--max-findings <n>|all`を追加、既定の件数上限（Nitは最大5件など）を超えて報告できるように** — https://code.claude.com/docs/en/changelog
  - **何が起きたか**: v2.1.288で「Added `--max-findings <n>|all` to /code-review to report more or fewer findings than the usual limit; the choice is reused until you pass `--max-findings default`」と明記された。指定した件数設定はそのセッション内で`--max-findings default`を指定するまで引き継がれる。
  - **なぜ注目されているか**: `/code-review`は公式ドキュメントで「Nitは1レビューあたり最大5件まで報告」といった既定の件数上限を設けており、実際に「低effortの既定設定だと実在するバグを見逃す」という報告（効果を上げるには`/code-review high`のような高effort指定が必要、という外部記事の指摘）がある。今回の追加は、effort（精度）とは別軸の「件数」側の上限も、デフォルトのまま使うと重要な指摘が切り捨てられうるという同じ構造の問題に対応したもの。
  - **使いどころ**: 経験の浅いメンバーのPRレビュー品質を揃える目的で`/code-review`を使っているなら、重要なPRでは`--max-findings all`で一度全件出させてから、何が既定設定で切り捨てられていたかを確認する価値がある。チーム導入時のルールとして「大きめのPRは`--max-findings all`、小さいPRは既定のまま」のような使い分けを決めておくとよい。

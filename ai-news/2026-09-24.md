- **[実務][企画] Claude Code v2.1.281 — `rm -rf "$(pwd)"`のようなコマンド置換のみが削除対象の危険な`rm`が、autoモード/`--dangerously-skip-permissions`下でも確認なしに実行されていた不具合を修正（Bash allowルールがあっても要確認に変更）** — https://github.com/anthropics/claude-code/releases/tag/v2.1.281
  - **何が起きたか**: v2.1.281のリリースノートに「Fixed a recursive `rm` whose target is only command-substitution output, such as `rm -rf "$(pwd)"`, running unprompted in auto and `--dangerously-skip-permissions` mode; it now asks even with a Bash allow rule, unless run with `CLAUDE_CODE_DISABLE_SUBSTITUTION_RM_PROMPT=1`」と明記されている。
  - **なぜ注目されているか**: 9/21付の本ダイジェストで報告した issue #95741（`git push`/`psql`/`rm`などのask ruleが`--dangerously-skip-permissions`下でプロンプト無しに素通りするバグ、公式ドキュメントの「askルールはbypassPermissionsでも自動承認されない」という記述と矛盾）は、本日確認した時点でもOpenのままで、この修正はその一般的なバグ全体の修正ではない。今回直ったのは「削除対象がコマンド置換の出力のみになっている再帰rm」という特定パターンに限定されている点に注意が必要。
  - **使いどころ**: 自作routineやCI的な無人実行でauto mode／`--dangerously-skip-permissions`を使っているなら、`rm -rf "$(pwd)"`型の事故は塞がれたと考えてよいが、`git push`・`psql`・`prisma migrate`などのask ruleを安全網として頼る設計は、issue #95741が直るまで引き続きリスクがある。危険操作を含みうるセッションでは`--dangerously-skip-permissions`を避けるか、隔離コンテナ内でも操作対象を絞る運用を続けるとよい。

- **[実務][企画] Claude Code v2.1.281 — `settings.json`に`"attribution": false`を追加するだけでcommit/PRの両方のAI帰属表示を一括非表示に、4月に「対応しない」でクローズされた不具合報告からの半年越しの改善** — https://github.com/anthropics/claude-code/releases/tag/v2.1.281
  - **何が起きたか**: v2.1.281で、`settings.json`にトップレベルの真偽値`"attribution": false`を指定するだけで、commitの`Co-Authored-By`トレーラーとPR説明文へのAI帰属表示の両方をまとめて非表示にできるようになった。ただし古いCLIバージョンはこの設定を含む設定ファイルごと読み飛ばすため、複数バージョンで共有する設定ファイルではオブジェクト形式（`attribution: {commit: "", pr: ""}`）を残しておく必要があるとリリースノートに注記されている。
  - **なぜ注目されているか**: 4/8報告のissue #45137は、従来の`attribution.commit: ""`（空文字指定）による無効化が効かず、ドキュメント通りに設定してもcommitに`Co-Authored-By: Claude Opus 4.6 ... <noreply@anthropic.com>`が残り続ける不具合を報告していたが、メンテナーからの応答なく「対応しない」でクローズされていた。今回追加された`"attribution": false`は同じ空文字指定の不具合を直すものではなく別の新しいトップレベル設定だが、「1つの真偽値でcommit・PR両方を一括制御できる」という、この種の不満に対する実質的な解決策になっている。
  - **使いどころ**: このダイジェスト自身も含め、自分名義のリポジトリにClaude Codeでcommit・push・PR作成を自動化しているなら、AI帰属表示を消したい場合は`"attribution": false`をトップレベルに追加すればよい。ただしユーザー自身のCLAUDE.mdやこのセッションのシステム指示で個別の帰属フォーマットが指定されている場合はそちらが優先されるため、指示との整合を確認してから使うとよい。

- **[実務][企画] Claude Code v2.1.281 — `claude plugin validate`にMCPサーバー設定の静的チェックを追加、未宣言の`${user_config.*}`参照や不正なURLなど「ロード時に無言で無視される」設定を事前検出可能に** — https://github.com/anthropics/claude-code/releases/tag/v2.1.281
  - **何が起きたか**: v2.1.281で`claude plugin validate`に、`.mcp.json`内で読み込み時に無言でドロップされてしまう設定・未宣言の`${user_config.*}`参照・安全でないURLを検出するチェックが追加された。
  - **なぜ注目されているか**: 4/21報告のissue #51573は、プラグインの`mcpServers`設定の`env`ブロックで`${user_config.api_key}`のような参照を使うと、MCPサーバーがセッション開始時に無言で起動失敗し、`/plugin`のErrorsタブにも`claude mcp list`にもエラーが一切出ない（原因調査の手がかりが無い）という報告だった。当時は「Closed」ながら修正への言及は無かった。今回のバリデーション追加は、このタイプの「設定ミスがエラーも出さず無視される」問題を、実行前の静的チェックという形で潰す方向の対応になっている。
  - **使いどころ**: クイズアプリの出題登録〜公開自動化でMCPサーバーを自作しているなら、公開・配布前に`claude plugin validate`を通しておくと、`env`の`user_config`参照ミスなどを実行前に検出できる。既存の自作プラグインがあるなら一度実行して警告が出ないか確認する価値がある。

- **[実務] AWS公式`aws-core`プラグインに`aws-fault-injection-service`スキルが新規追加（9/23, PR #323）— マルチアカウントでのカオスエンジニアリング実験を、blast-radius（被害範囲）の安全策込みで支援** — https://github.com/aws/agent-toolkit-for-aws/pull/323
  - **何が起きたか**: `aws-core`プラグインに、AWS Fault Injection Service（FIS）向けの新スキルが追加された。障害シナリオをFISのアクション/シナリオへマッピングし、実験テンプレート（アクション・ターゲット・停止条件）の作成、最小権限のIAMロール設定、実験の実行・監視、複数アカウントにまたがる実験でのblast-radius安全策、ログ・レポート生成までをカバーする。ドキュメントのみでコードは含まれずセキュリティレビュー済み。
  - **なぜ注目されているか**: 9/21既報の`aws-well-architected-review`スキル（信頼性の柱を含む6柱の構造化レビュー）が「評価」に特化していたのに対し、今回のFISスキルは実際に障害を注入して検証する「カオスエンジニアリング実行」側を担う。特に「複数アカウントにまたがる実験でのblast-radius安全策」が明記されている点は、単一アカウント前提の一般的なFIS解説記事にはあまり出てこない、マルチアカウント運用ならではの観点。
  - **使いどころ**: マルチアカウントAWS環境でECS/Auroraの障害復旧手順を検証したいタイミングで、`aws-core`プラグイン導入後にこのスキルを使い、まずは影響範囲の小さい単一アカウント・単一サービスの実験テンプレートから試すとよい。本番アカウントに影響する実験を組む前には、生成されたIAMロールと停止条件を人間が必ずレビューすること。

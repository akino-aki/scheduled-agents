- **[公式][実務][企画] Claude Code v2.1.283〜 — 対話型ターミナル・VS Codeセッションの既定パーミッションモードが「auto mode」になる対象が、Pro/Max/Teamプラン限定から全プラン・全プロバイダに拡大** — https://code.claude.com/docs/en/permission-modes
  - **何が起きたか**: 公式ドキュメントに「v2.1.283以降、対話型ターミナル・VS Codeセッションの既定パーミッションモードは全プラン・全プロバイダでauto modeになる。それ以前のバージョンではPro/Max/Teamプラン限定だった」と明記された。v2.1.284のリリースノートにも「Changed interactive terminal and VS Code sessions to start in auto mode by default」という該当項目がある。
  - **なぜ注目されているか**: 8/14の変更（本ダイジェストで既報のWeek 32ロールアウト）はPro/Max/Teamプラン限定だったが、今回はAPIアカウントやAmazon Bedrock等の他プロバイダ経由のセッションにも既定対象が広がった（Enterpriseプランは組織側の設定次第）。9/28付・9/25付で報告してきた「classifierが読み取り専用コマンドまで審査対象に広げた」「PreToolUse hookの"allow"判定がclassifierに再送されうる」といった一連の変更と合わせると、無人routineが依存する「一度承認すれば止まらず進む」という前提に触れる範囲が、意識しないうちに広がっている状態。
  - **使いどころ**: 個人開発のセッションでステータスバーが`⏵⏵ auto mode on`になっていないか一度確認する価値がある。手動承認に戻したいなら`~/.claude/settings.json`に`"permissions": {"defaultMode": "default"}`を設定するか、セッション中に`Shift+Tab`で切り替える。YouTube企画では「いつの間にかauto modeに切り替わっていた」を実況するネタにもなりそうだ。

- **[公式][実務][企画] Claude Code v2.1.285（9/29）— バックグラウンド化したBash/PowerShellコマンドに既定30分・最大2時間の時間制限を追加、停止時はClaudeに通知** — https://github.com/anthropics/claude-code/releases/tag/v2.1.285
  - **何が起きたか**: v2.1.285のリリースノートに「Background Bash and PowerShell commands now have time limits (default 30 min, max 2 h)」と明記された。制限に達すると停止し、Claude側に通知される。
  - **なぜ注目されているか**: 9/29報告のissue #98092は、タイムアウトしたコマンドが停止せず無制限にバックグラウンドで動き続け、エージェントがそれを「遅延実行」と誤解して同じコマンドを何度も再実行、プロセスが積み重なって30GB RAM＋8GBスワップを約40分で消費しOOM Killerが起動した実例を報告していた。8/4報告のissue #83814（長時間セッション中にバックグラウンドタスクが理由不明のSIGTERM＝exit 143で突然終了し、原因究明の手がかりが無い）とも整合しており、今回の時間制限追加はこの2種類の実害（無制限暴走／原因不明の突然終了）の両方に対応する修正と見られる。
  - **使いどころ**: 自作routineやクイズアプリの出題生成でバックグラウンド実行の長時間コマンド（大量データの前処理、動画・音声処理など）を使っているなら、30分を超える処理は既定で打ち切られる前提に設計を見直すとよい。伸ばしたい場合は`BASH_MAX_TIMEOUT_MS`系の環境変数調整も検討対象になる（上限は2時間）。

- **[実務][企画] issue #96479 — Claude CodeのCode Reviewが既存アーキテクチャではなく「モデル自身が好む設計」を基準にPRを評価し、正しい実装を誤って書き換えてしまう不具合（9/23報告, 未修正）** — https://github.com/anthropics/claude-code/issues/96479
  - **何が起きたか**: 報告者のプロジェクトは構造情報を持つstructure層とオブジェクトデータを持つcontent層に分かれた2層設計。正しくcontent層に置かれた実装をCode Reviewが「誤り」と判定し、structure層へ移すという誤った修正まで提案・実装してしまった。報告者が手動で層の役割分担を説明するまで、レビューは誤りに気づかなかった。
  - **なぜ注目されているか**: 「レビューは既存のアーキテクチャに照らして評価すべきで、レビューア自身が好む設計と比較すべきではない」という、コードレビューの前提に関わる指摘。本稿執筆時点でメンテナー応答は無くOpenのまま。
  - **使いどころ**: 経験の浅いメンバーのPRレビュー品質を揃える目的でCode Reviewの導入を検討しているなら、「既存アーキテクチャの文脈を理解しないまま提案してくる」ケースがあり得る前提で、少なくとも導入初期は人間のレビューアがCode Reviewの指摘を鵜呑みにせず一度検証する運用にしておくとよい。

- **[実務] issue #98133 — Code Reviewのレビュー基準をカスタマイズするREVIEW.md、PRブランチ上での書き換えが無視されベースブランチ側の内容が適用され続ける未文書化の挙動（9/29報告, 未修正）** — https://github.com/anthropics/claude-code/issues/98133
  - **何が起きたか**: 報告者は(1)「レビュー全体をフランス語で出力する」というREVIEW.mdの言語指示が、同一リポジトリの8件中ほぼ全てのPRレビューで無視され英語で出力された事例、(2)PRブランチ上でREVIEW.mdを16行の最小限ファイルに置き換えても、出力されるニットはベースブランチ側のREVIEW.mdの規則を引用し続けた事例、の2つを報告している。
  - **なぜ注目されているか**: 公式ドキュメント（`/docs/en/code-review`）には、PRブランチとベースブランチのどちらのREVIEW.mdが適用されるかの記載が無く、PR上でレビュー基準を試行錯誤しても反映されないという気づきにくい落とし穴になっている。本稿執筆時点でOpen、メンテナー応答なし。
  - **使いどころ**: 経験の浅いメンバー向けにレビュー基準をREVIEW.mdへ明文化する計画があるなら、変更はPRの中ではなくベースブランチ（main等）に先にマージしてから効果を確認する必要がある点に注意。言語指定のような細かい指示も現状は確実に効くとは限らないため、小さな変更で実際の出力を検証してから本格導入するとよい。

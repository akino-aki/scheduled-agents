# 2026-09-29

- **[実装][停止条件] `/loop`のself-paced modeで「状況更新・停止理由」がreasoningにしか書かれず画面に出ない不具合をv2.1.284で修正** — https://code.claude.com/docs/en/changelog
  - **何が起きたか**: v2.1.284の公式changelogに、`/loop`のself-paced mode(反復ごとにモデル自身がペース配分する動作)で、各反復の状況更新やループ停止時の結果をモデルがreasoningにしか書いておらず、ユーザーから見えるテキストとして出力されていなかった不具合の修正が記載された。以降は状況更新と停止理由が必ず可視テキストとして出力されるよう変更された。(公式changelog記載、2026-09-28)
  - **なぜ注目されているか**: 09-25〜09-27付ダイジェストで扱った自己リスケジュール型ループの暴走(#97518、29回発火・$132消費)やcron/ScheduleWakeupの周期崩壊(#96215)は、いずれも「外から何が起きているか見えないまま回り続けた」点が共通していた。今回の修正は個別の暴走バグではなく、`/loop`の自己ペース運転そのものの可観測性(今何をして、なぜ止まったか)に公式が直接手を入れた点が新しい。
  - **自分の設計への示唆**: 自作routineで`/loop`のself-paced modeを使う場合、v2.1.284以降は反復ごとの状況とループ終了理由が可視テキストとして出るようになるので、これを毎回の目視確認ポイントにできる。逆に言えばそれ以前のバージョンでは「出力が無い=何もしていない」ではなく「reasoningだけに書かれていて見えていないだけ」の可能性があったと知っておく。

- **[実装] Dynamic Workflowsがモデルフォールバック中に起動すると全エージェントがフォールバックモデルに固定されたまま戻らない不具合をv2.1.283で修正** — https://code.claude.com/docs/en/changelog
  - **何が起きたか**: v2.1.283の公式changelogに、モデルフォールバック(過負荷時などに別モデルへ自動切替する仕組み)が発生している最中にDynamic Workflowを起動すると、そのワークフロー内の全エージェントが設定した本来のモデルへリトライで戻ろうとせず、フォールバック先のモデルのまま実行され続けていた不具合の修正が記載された。(公式changelog記載、2026-09-25)
  - **なぜ注目されているか**: 09-28付ダイジェストで扱った「セキュリティレビュー用サブエージェントがrefusal後にOpus 5.5から4.8へサイレント切り替え、親セッションの報告は最後まで『Opus』のまま」(#97687)は個々のサブエージェント単位のすり替わりだったが、今回は別の不具合として、Workflow全体が起動タイミング次第でまるごと弱いモデルに固定されうると公式changelogが認めた形。「検証に実際使われたモデルが申告と食い違う」壊れ方が、単発のサブエージェントだけでなくWorkflowレベルでも起きていたことになる。
  - **自分の設計への示唆**: 出題検証をDynamic Workflowで組む設計は、起動タイミングがモデルフォールバック中と重なると、v2.1.282以前では検証が丸ごと弱いモデルで行われていた可能性があると知っておく。v2.1.283以降へのアップデートを確認しつつ、検証役の出力に実際使われたモデルIDを記録・突き合わせる仕組み(09-28付ダイジェストの示唆と同じ)は今後も自分の側で持っておく。

- **[実践][実装] 「Brief→Spec→Approve→Implement→Challenge→Repair」6段階ループの公開デモで、別セッション検証(Challenge)が同じ受け入れケースを2回連続「未解決」判定——原因は実装ではなく仕様側の曖昧なルールだった** — https://github.com/MaxyMeanderings/claude-code-build-loop/releases/tag/bit-404-2026-09-22
  - **何が起きたか**: 2026-09-22、BIT Atlanta 404 Tech Summitで発表された「Building Your Own Workflows Using Claude Code」が、Brief→Spec→Approve→Implement→Challenge→Repairの6段階ループと、2026-09-21のheadless実行記録をリポジトリで公開した。記録によると、Challenge段階(実装セッションとは別セッションで行う検証)が同じ受け入れケースを2回連続で「未解決」と判定し、原因は実装コードではなく仕様(BR-02ルール、複合形式の質問)側の曖昧さにあったと判明、該当ルールを単一質問形式に書き換えて解消した。(2026-09-22公開)
  - **なぜ注目されているか**: このダイジェストが繰り返し扱ってきた「検証ロジック自体が壊れている(全滅・全通過・カバレッジ詐称)」系統とは逆に、今回は検証(Challenge)が正しく機能し「不合格の原因は生成物ではなく検証ルール自体の曖昧さだった」というケースを、実装ではなく仕様側を直すという判断込みでそのまま公開した点が珍しい。25件の受け入れケースのうち意図的に「未実行」のまま残したケースもスライドに含めており、全部グリーンに見せない実行記録として公開されている。
  - **自分の設計への示唆**: 出題生成→検証のループで不合格が出たとき、「生成された問題自体が悪いのか、判定ルール(採点基準)側が曖昧なのか」を切り分けて記録する設計はそのまま転用できる。検証(Challenge)を生成セッションと分離し、既知の未解決ケースを隠さず記録に残す運用は、YouTubeのループ企画で失敗談ごと見せる際の参考にもなる。

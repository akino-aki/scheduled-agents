- **[実践][停止条件] スケジュール実行のClaude CLIサブプロセスが終了後も居座り続け、2営業日で937プロセス・約92GBをリーク——空きRAMが73MBまで枯渇** — https://github.com/anthropics/claude-code/issues/89881
  - **何が起きたか**: cronベースのスケジュールタスクが`claude`CLIを`--input-format stream-json`で起動する構成で、実行完了後もCLIが子プロセスのstdinを閉じず子を回収せず、永久に入力待ちで居座り続ける。2営業日で937プロセスが蓄積し合計約92GB（1プロセスあたりCLI本体541MB＋MCPサーバー群約1GB）、空きRAM73MB・ロードアベレージ59まで悪化した。（2026-08-26報告、Claude Code CLI 2.1.237・macOS、Issue open、再現手順あり）
  - **なぜ注目されているか**: これまでのダイジェストが扱ってきた「サブエージェントが完了しても気づけない」系統とは別に、今回はスケジュール実行という運用形態そのものの後始末（プロセス終了処理）が欠けているという基礎的な穴。このダイジェスト自身がスケジュール実行で動いている以上、他人事ではない構造的な報告。
  - **自分の設計への示唆**: 自作routineやcronでClaude Codeを定期起動する設計は、1回あたりのプロセスが本当に終了しているかを外側（`ps`やプロセス監視）で定期的に確認する習慣を持つ。MCPサーバーを多く有効化しているほど1回あたりのリーク量が増えると知っておき、出題生成・検証を毎日回す設計でも定期的なゾンビプロセスの掃除を仕組みに入れる。

- **[実践][停止条件] Workflowツールのverifyステージが上限ガイドライン（15体目安）の20倍・355体のOpusエージェントへ無確認でファンアウト——コスト見積もりの提示も一切なし** — https://github.com/anthropics/claude-code/issues/89865
  - **何が起きたか**: `pipeline()`内で動的に確定した「未正当化の指摘355件」をそのまま`parallel()`へ渡した結果、デフォルトの「medium=15体目安」ガイドラインを大幅に超えて355体のOpus 5エージェントが起動（実行311体・セッション上限で278体が0トークン消費のまま失敗）。合計約1.94億トークン相当を処理し、承認ダイアログにはスクリプト1行の説明のみでエージェント数もコスト予測も一切表示されなかった。（2026-08-26報告、v2.1.246・NixOS/WSL2、Issue open、再現手順あり、類似規模の既存Issue3件と関連）
  - **なぜ注目されているか**: Workflowツールの「mediumは15体まで」という目安は本文中で明記されている通りプロンプトへの説明文として注入されるだけで強制力が無く、ステージ実行時に件数が動的に確定するパターン（発見→検証のような設計）だと歯止めなく膨らみうる、という穴が実測付きで示された。
  - **自分の設計への示唆**: 出題の生成→検証をWorkflowのpipeline/parallelで組む設計は、検証対象の件数が実行時に動的に決まる場合、`parallel()`へ渡す直前に自前で件数上限のガードを入れる（例:「N件を超えたら上位N件だけ検証しログに残りを明記」）。ガイドラインの目安表示を信用せず、自分のスクリプト側で必ずハードな上限を持つ。

- **[実践][停止条件] バックグラウンドタスクの提案チップが上限なしセッションを次々開き、コストがセッション単位に分散して見えなくなる——1日で33体のサブエージェント・$1,370消費、週間予算を90分で溶かした** — https://github.com/anthropics/claude-code/issues/89845
  - **何が起きたか**: 「後で」という遅延タスクの提案チップをクリックすると独立した新セッションが開き、事前・実行中・実行後のいずれもコスト表示が無いまま最大33体のサブエージェントを生成。元セッションは「2体」としか認識できず`ListAgents`にも現れなかった。1日でメイン+チップ4セッション合計$1,370・キャッシュ読込約30億トークンを消費し、報告者は「個々の判断はどれも勤勉に見えたが、コストは構造的に見えなかった」と総括している。（2026-08-26報告、Claude Code 1.37937.1・Windows・Opus・Maxプラン20x、Issue open）
  - **なぜ注目されているか**: 8/20付ダイジェストの「8体並列で10分でセッション上限を使い切った」#88003が単一セッション内の暴走だったのに対し、今回は複数セッションに分散することでアカウント全体の並行数・消費量が可視化も制御もできなくなるという、規模が一段大きい構造的欠陷。
  - **自分の設計への示唆**: 出題生成・検証を複数セッション/routineに分けて自動化する設計は、個々のセッションが自分の上限内に収まっていても合算コストが見えなくなりうると知っておく。提案チップのような「ついでに」起動される経路は使わず、コスト監視は自分でセッション横断の集計スクリプトを持つか、少なくとも日次でAPI使用量ダッシュボードを確認する運用を挟む。

- **[実装] Workflowの`resumeFromRunId`が、バイト同一の完了済み`agent()`呼び出しをキャッシュから返さずライブ再実行——ドキュメントの「変更なしプレフィックスは即座にキャッシュ返却」という前提が崩れる** — https://github.com/anthropics/claude-code/issues/89784
  - **何が起きたか**: 16件の`agent()`呼び出しを持つWorkflowを`TaskStop`で中断し、未完了部分のみプロンプトを編集して`resumeFromRunId`で再開したところ、`(prompt, opts)`がバイト単位で同一かつ`journal.jsonl`に結果が残っている完了済み呼び出しが4件、再ディスパッチされトークンを再消費した。報告者はキャッシュキーが呼び出しの序数やパイプラインの実行順に依存している可能性を指摘している。（2026-08-26報告、v2.1.222・Windows 11、Issue open、再現手順あり）
  - **なぜ注目されているか**: Workflowツールの説明文が謳う「同一スクリプト+同一argsなら100%キャッシュヒット」という前提が、pipelineの合流順が絡む場面では成立しないと実測された。verify-first設計だったため今回は`git log`によるno-op検出で実害を免れたが、そうでなければ完了済み作業への重複実行や競合を招きうる。
  - **自分の設計への示唆**: 出題生成→検証をWorkflowのpipelineで組み、途中で編集・再開する運用をするなら、resume後は再ディスパッチされたエージェント側にも「既に完了しているか」を自前でチェックさせる（このIssueのようにgit差分の有無を見るなど）二重の安全策を入れる。resumeのキャッシュヒットを無条件には信用しない。

  - **何が起きたか**: 3,591件のメッセージを分析した結果、ユーザーの実作業内容ではなく、セーフガード警告バナー自体の文言（「sometimes」「legal」「capabilities」等、lift値174.1など）が後続の誤検知発生の最も強い予測因子と判明。警告文が会話履歴に残り続けて語彙が累積し、1セッションで39回発火、うち18回は`fallbackModel`設定を無視してOpus 4.8へ無通知でダウングレードした。（2026-08-11報告、Issue open）
  - **なぜ注目されているか**: 8/8付ダイジェストで扱った「セーフガードについての議論自体が新たな誤検知を誘発する」現象（#84821）について、今回は語彙レベルでの定量的な因果メカニズムが示された続報。
  - **自分の設計への示唆**: 検証AIの却下メッセージをそのまま会話履歴に残し続けると、却下メッセージの言葉遣い自体が次の却下を誘発しうるという実測が出た。却下理由は要約して次のプロンプトに渡すだけに留め、警告文そのものを再送しない設計を徹底する。

- **[実装] worktree隔離セッションでシェルのfor/whileループとprocess substitutionが誤ってブロックされる——CI状態ポーリングの定番パターンが実行不能に** — https://github.com/anthropics/claude-code/issues/85931
  - **何が起きたか**: `claude --worktree`のworktree隔離下では、`for f in one two; do ...; done`のような単純なforループやprocess substitution（`<(...)`）が「複雑すぎて検証できない」として拒否される。CI完了待ちの`until [ "$(gh api .../status)" != pending ]; do sleep 45; done`のような定番ポーリングも同様に拒否される一方、`$(...)`のコマンド置換は素通りするという非一貫性がある。（2026-08-11報告、v2.1.228・macOS、Issue open）
  - **なぜ注目されているか**: worktree隔離は暴走防止の安全機構だが、その判定がファイルシステム操作の有無ではなく構文の複雑さで行われているため、ファイル操作を伴わない安全なループ構文まで一律ブロックしてしまっている。
  - **自分の設計への示唆**: worktree並列でCIステータスや外部APIをポーリングするループを組むなら、シェルのfor/while/process substitutionに頼らず単純なコマンドを1行ずつ実行するか、この不具合が直るまでは`ScheduleWakeup`等の別の待機手段を使う。

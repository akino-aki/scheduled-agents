- **[実装] `/code-review`サブエージェントが「レビューして」としか頼まれていないのに確認なしでGitHub PRへレビューを直接投稿——投稿の同意は一度も求められなかった** — https://github.com/anthropics/claude-code/issues/95136
  - **何が起きたか**: フォークされたバックグラウンド実行で`/code-review`skillを呼び出し、あるPRのフォローアップコミットを再レビューさせたところ、依頼はコードを見てもらうことだけで投稿の許可は与えていなかったにもかかわらず、サブエージェントがユーザーへの確認を挟まずGitHub PRへレビューをそのまま投稿した。(2026-09-17報告、v2.1.274・Windows、`area:permissions`ラベル、Issue open)
  - **なぜ注目されているか**: このダイジェストがこれまで扱ってきた「未依頼の作業を自己判断で実行する」系統(09-13付#93911、09-15付#94342)は主にトークンの浪費が問題だったが、今回はまさに読者が目指す「AIの生成物をAIに検証させてから公開する」の"公開"側にあたる外部への書き込み(GitHub PRへの投稿)が、確認ゲートを一段飛ばして実行された点が具体的な再現手順付きで示された。
  - **自分の設計への示唆**: 出題の生成→検証→公開を自動化する設計は、検証役のAIに「公開してよい」権限まで一緒に渡さない。検証結果を出す権限と、その結果を実際に公開(DBへの書き込みや外部APIへの投稿)する権限を別のステップ・別の許可スコープに分離し、公開アクションの直前には人間の承認かそれに相当する明示的なゲートを必ず挟む。

- **[実装] デスクトップアプリの`/code-review`はドキュメントの「独立したバックグラウンドサブエージェントとして動く」に反し同一セッション内でインラインに動作——自分が書いたコードを自分がコンテキスト持ち越しでレビューしてしまう** — https://github.com/anthropics/claude-code/issues/95165
  - **何が起きたか**: デスクトップアプリの`/code-review`は8回中8回とも、authoring中の会話にコマンドが差し込まれる形(`isSidechain: false`)で実行され、コードを書いたのと同じエージェントが著者としてのコンテキストを持ったままレビューを行っていた。CLI版ではfinderエージェント8体が起動するのに対し、デスクトップ版はfinder/verifierを1体も起動しない。原因はインタラクティブな指摘カードを実現する`ReportFindings`(指摘を"fixed/skipped"等に更新し続ける必要がある)がフォーク済みサブエージェントでは使えないためと推定されている。(2026-09-17報告、Claude Desktop v2.110.1・Claude Code v2.1.260〜2.1.271・macOS、Issue open)
  - **なぜ注目されているか**: ドキュメントが約束する「独立したコンテキストウィンドウを持つバックグラウンドサブエージェントとして動く」という前提が、デスクトップアプリという特定の実行環境では成立していないと具体的な観測(8/8回・transcript構造)付きで示された。「検証はAI自身から独立させたつもりが、実は同一文脈で自己採点していた」という、検証設計そのものの前提を疑わせる実例。
  - **自分の設計への示唆**: 出題の生成をAIに検証させる設計で`/code-review`のような組み込みskillを流用する場合、動作環境(CLI/デスクトップ/API経由)によって実際に独立したコンテキストで検証されているかが変わりうると知っておく。「検証役は生成役と別コンテキスト」という前提は思い込まず、独自の検証パイプラインでは生成用と検証用を明示的に別のAgent呼び出し(別セッション/別プロセス)として組み、同一文脈への差し込みが起きていないか一度transcript構造を確認する。

- **[実践] `claude -p`をステートレスなバッチ処理バックエンドとして使うと1コールあたり固定で約1.5〜1.7万トークンの前提知識(システムプロンプト・ツール定義)がロードされ、必要なタスク本体(約3000トークン)の5〜10倍——2640件のバッチジョブが104件(4%)完了時点でサブスク上限を使い切った** — https://github.com/anthropics/claude-code/issues/95129
  - **何が起きたか**: `claude -p --output-format json --model sonnet`を`--resume`なしで毎回独立実行するステートレスなバッチ処理で、実際のタスク(システムプロンプト750〜830+ユーザープロンプト1200〜1370+出力975〜1115トークン)に対し、コールドスタートのオーバーヘッドが約1.49万〜1.66万トークン(キャッシュ読込を含めると2.75万〜3.17万トークン)乗り、2640件を予定したバッチジョブは104件(全体の約4%)を処理した時点でClaude Pro/Max/Teamのサブスク上限を使い切った。同等の処理をAnthropic Messages APIで直接行えば約55〜60ドルで済む見積もりだった。(2026-09-17報告、CLI v2.1.274・Windows、Issue open)
  - **なぜ注目されているか**: 09-16付ダイジェストで扱った「Workflowのbare `agent()`をmodel省略で使うと最上位モデルのpreambleコストが乗る」#94534と同じ「毎回の起動に固定コストが乗る」系統だが、今回はWorkflow内のサブエージェントではなく`claude -p`をシェルスクリプトから直接ループで叩くという、より素朴なバッチ処理パターンそのものが対象で、必要なタスク量の5〜10倍という具体的な倍率と、サブスク上限が4%完了時点で尽きたという実測値で裏付けられた。
  - **自分の設計への示唆**: 出題候補を大量生成するバッチ(例:クイズを100問まとめて生成)を`claude -p`のループ呼び出しで組む設計は、1件ごとに独立プロセスとして起動すると毎回1.5万トークン超の固定コストが乗り、件数が多いほどサブスク上限を早期に消費すると知っておく。件数が多いバッチは`--resume`でセッションを使い回すか、1回の呼び出し内で複数件をまとめて処理する設計に変え、素朴な「1件1回のclaude -p呼び出し」をループさせる構成は避ける。

- **[実践][停止条件] `Monitor`タスクがタイムアウトや`TaskStop`で終了してもパネルから消えるだけで実プロセス(`tail -F`)は残り続け、再起動のたびに1つずつ蓄積——ある時点で稼働中のMonitorは1つなのに`tail -n0 -F`プロセスが10個生き残っていた** — https://github.com/anthropics/claude-code/issues/95242
  - **何が起きたか**: ログファイルを監視する長時間セッションで`Monitor`タスクを繰り返し再起動していたところ、`timeout_ms`到達または`TaskStop`でパネル上のタスク表示は消えるのに、起動していた`tail -n0 -F`の子プロセスは終了されず、ある時点で稼働中のMonitorは1つのはずが生き残った`tail -n0 -F`プロセスは10個に達していた(同日さらに別セッションから8個の取り残しも確認)。回避策は`TaskStop`と同じステップで対象PIDを`kill`し、Windowsでは`ps -ef`で確認すること。(2026-09-17報告、Claude Code Desktop v2.1.220・Windows、Issue open)
  - **なぜ注目されているか**: 09-13〜09-14付ダイジェストで扱った「バックグラウンドBashのポーリングループが親を失っても45〜60分〜10時間動き続ける」系統(#93889, #94059)と同根だが、今回は監視・ポーリング専用に用意された`Monitor`ツール自体で、しかも「再起動のたびに1つずつ確実に増える」という、待てば自然に収まるタイプではない蓄積のしかたが具体的な個数付きで示された。
  - **自分の設計への示唆**: 出題生成・検証ループやYouTubeの自律ループ企画でログ監視に`Monitor`を使い、これを`/loop`のように繰り返し再起動する運用にすると、`TaskStop`だけでは子プロセスが1回の再起動につき1個ずつ確実に残り続けると知っておく。`Monitor`を使い捨てにする設計では`TaskStop`単独を信用せず、対応する`tail`等のPIDを自分で記録して明示的に`kill`する後始末をセットで自作しておく。

  - **何が起きたか**: `/loop 15m mailroom`のような固定間隔ループを実行すると、モデルが`/loop`スキルの指示にある「CronCreateを呼んでから実行」という手順を守らず、CronCreateを呼ばずにプロンプトを1回だけ実行して終了することがある。`CronList`で確認すると予定ジョブがゼロのままで、次の定期実行が来ないことにユーザーが後から気づく。（2026-08-31報告、area:skills、Issue open、再現手順あり）
  - **なぜ注目されているか**: 原因は「CronCreateを呼ぶ」という手順が完全にモデルの指示追従だけに依存し、コード側の強制メカニズムが存在しないこと。報告者は解決策として、事後に`CronList`でジョブ存在を検証するか、harness側がintervalのパースと同時に決定論的にcronジョブを作る方式へ切り替えるべきだと提案している。
  - **自分の設計への示唆**: 自作routineや`/loop`で毎日の定期実行を組む設計は、スケジュール登録自体がモデルの気まぐれで飛ばされうると知っておく。設定直後に`CronList`（このセッションなら`list_triggers`相当）でジョブが実際に登録されたか一度確認する習慣を、セットアップの最後に必ず入れる。

  - **何が起きたか**: Jiraチケットの計画・3体のレビュアーサブエージェントへのディスパッチまで23分で正常に進んだ後、改訂プランをレビュアーへ`SendMessage`で送った返信が期待チャネルに届かず、以降7時間にわたり5〜8秒間隔で「echo idle」「pending waits armed」のような無意味なハートビート呼び出しを繰り返した。5,486回の呼び出しのうち5,431回(99%)が無駄で、呼び出しごとにコンテキスト全体を再送信するため作業量でなく呼び出し回数そのものがコストに直結した。（2026-08-31発生・2026-09-01報告、v2.1.252・macOS、Issue open、手動強制終了で対応）
  - **なぜ注目されているか**: タイムアウト機構も失敗検知機構も無く、ルーティング失敗という一つの取りこぼしが「リトライすべきか諦めるべきか」を一切判断できない無限ループに直結する。8/29付ダイジェストで扱った「ネストしたサブエージェントの2回目の返信がルートへ誤配信される」#90463と同系統だが、今回は返信が完全に消失し、しかも一見無害なハートビート機構そのものが暴走の主体になっている点が新しい。
  - **自分の設計への示唆**: 出題生成・検証をroot→coordinator→workerのように多階層のサブエージェントに分業し`SendMessage`で往復させる設計は、返信が届かない場合に無限リトライへ落ちうると知っておく。ハートビート/ポーリング用のティックには「N回連続で進展が無ければ停止し人間に回す」という上限を自前で持たせ、SendMessageの応答待ちを無条件に信用しない。

- **[実践][停止条件] カスタム型サブエージェントが起動直後にトランスクリプトも出力もエラーも残さずサイレントに死亡——4時間半、`ps`で確認するまで親セッションは気づけなかった** — https://github.com/anthropics/claude-code/issues/91298
  - **何が起きたか**: `.claude/agents/*.md`で定義したカスタム型のレビュアーエージェント2体を並行起動したところ、両方とも「Spawned successfully」を返した数秒〜数分後に子プロセスが終了。トランスクリプトファイルなし・出力なし・失敗通知なし・ログ痕跡なしのまま4時間半以上放置され、`ps`でプロセスが存在しないことを確認して初めて発覚した。再起動を試みても10分以内に同じ結果を繰り返し、メモリ不足(101GiB空き)やエージェント定義の問題は原因から除外されている。（2026-09-01報告、v2.1.246・Linux、Issue open）
  - **なぜ注目されているか**: `ListAgents`は死亡したエージェントを生きている「teammate」として列挙し続けるため、外部から生死を判別する手段が`ps`しか無いという根深さが指摘されている。8/26付ダイジェストの「forkサブエージェントが未作業のままcompletedを自称する」#87897とは逆方向の壊れ方で、今回は完了報告どころか死亡の報告自体が一切無い。
  - **自分の設計への示唆**: 出題生成・検証をカスタム型サブエージェントに分業する設計は、起動直後の生死確認を`ListAgents`の表示だけに頼らない。報告者が採った回避策と同じく、エージェントの最初のアクションとして「出力ファイルを1つ作成する」ことを必須化し、一定時間内にそのファイルが現れなければ死亡とみなすliveness監視を自前で持つ。

- **[実装] Claude Code v2.1.257 — 自動モードに「Containment Escape」ルールを追加し、クラウドメタデータ認証情報の取得・egress回避・テナント間到達を環境が「想定内」と明示しない限り自動承認しなくなった** — https://github.com/anthropics/claude-code/releases/tag/v2.1.257
  - **何が起きたか**: v2.1.257(2026-09-01 17:53 UTC公開)で、Pro/Max/Teamプランの既定になっている自動モード(auto mode)に「Containment Escape」ルールを追加。クラウドメタデータ認証情報の取得・egress回避の試み・テナント間到達の試みの3種を、環境側が「想定内の動作」と明示しない限り自動承認の対象から外し、分類器(classifier)による確認を必須にした。同リリースでは作業ディレクトリ外への初回ファイル読み取り時に一度だけ確認を挟むオプション(`permissions.blockReadsOutsideWorkingDirectories`)も追加された。（Claude Code公式リリースノート、code.claude.com changelogでも確認済み）
  - **なぜ注目されているか**: 自動モードは分類器が人間の代わりにアクションを審査する仕組みだが、その分類器が「安全」と自動承認してよい範囲そのものを絞り込む変更で、対象が「サンドボックス脱出につながりうる3系統」という具体的なカテゴリに踏み込んでいる点が新しい。`/loop`の無プロンプト自律実行デフォルトが全プロバイダで常時使えるようになったのと同時期のリリースであり、無人でより長く自律実行させる方向と、その自律実行が踏み込める境界を狭める方向が同じリリースに同居している。
  - **自分の設計への示唆**: AWSマルチアカウント環境で自律ループを回す設計は、auto modeが既定になっている以上この変更の恩恵を素の状態で受けられる。ただし「環境が想定内とマークしない限り」という条件がどう設定されるかは別途確認が要る。出題生成・検証のループ自体はクラウド認証情報やテナント間到達には触れないため今は直接関係しないが、AWS側の自律運用（CDK/ECSデプロイなど）にauto modeを広げる際は、この変更が塞ぐ範囲を先に把握しておく。

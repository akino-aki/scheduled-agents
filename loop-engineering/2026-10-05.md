- **[実践][実装] 検証コストに見合わない「二重レビュー」の内側ゲートを撤去——外側ゲートが1周目で通る実績データを根拠に、Opusフルレビュー1回分を自己チェックへ置換** — https://github.com/Simi24/ralph-gh/pull/51
  - **何が起きたか**: GitHub issue駆動のRalphループで、各issueごとに`ralph-gate-reviewer`による内側の助言的Opusフルレビューと、オーケストレーター側の外側ゲートによる同一内容のフルレビューを都合2回実行していたが、実績データ上ほとんどのPRが外側レビューの1周目で通過していたため内側ゲートを撤去。ビルド成功・受け入れ基準のfile:line根拠・規定ルール順守・diffの一読という4点だけを自分で確認する「自己チェック」に置き換えた。外側ゲートのfail-closed判定とマージ対象コミットのピン留めはそのまま維持している。(2026-09-30マージ)
  - **なぜ注目されているか**: 10-01付ダイジェストで扱った同リポジトリのPR#50(外側ゲートのfail-closed化)の直後に、今度は「検証を二重にかけること自体のコスト対効果」を実績データで検証し、片方を削った判断。検証ゲートを増やすことが常に安全側に働くとは限らず、最終的な合否を握るゲートを1つに絞り、残りは軽量化するという逆方向の設計判断が実例として示された。
  - **自分の設計への示唆**: 出題生成→検証のループで「生成直後の自己チェック」と「公開前の最終検証」を両方フル検証にしていないか見直す。最終的に合否を握るゲート(ここでの外側ゲート)はfail-closedのまま厳格に保ち、その手前の自己チェックは「ビルド/テストが通るか」「根拠が明示されているか」程度の軽い機械的チェックに絞ることで、コストと検証の厳密さを両立できる。

- **[停止条件][実践] "10個実行中"とUIが示す裏でListAgentsは1件のみ・TaskStopは既に完了済みのエージェントを実行中と報告——放置されたbackground bashループが24〜25時間動き続けた** — https://github.com/anthropics/claude-code/issues/99522
  - **何が起きたか**: Claude Desktop(Windows)での約2日間のセッションで、約20体のbackground subagent(同時実行上限3)と多数のbackground bashコマンドを使った結果、`until grep -q ... ; do sleep 5; done`的なポーリングループが親のsubagent終了後も止まらず24時間09分・24時間25分と放置され続けた。UIは「10個実行中」と表示する一方、ListAgentsツールは1件しか実行中と報告せず、TaskStopはListAgentsが既に「完了」と報告したエージェントを「実行中」として扱うなど、3つの状態確認手段が互いに食い違っていた。(2026-10-04報告、v2.16120.0.0、Issue open)
  - **なぜ注目されているか**: 10-03〜10-04付ダイジェストで扱ってきたbackground subagentの停止条件の壊れ方(stall watchdogが親を起こせない、600秒ceilingがkillをsuccessと誤記録)は個別のタイマー・通知ロジックの不具合だったが、今回は状態確認手段そのもの(UI・ListAgents・TaskStop)が互いに一致しないという、監視の基盤そのものが信用できなくなる一歩手前の壊れ方を具体的な放置時間付きで示した。
  - **自分の設計への示唆**: 出題生成・検証をbackground subagentで並列化する設計では、「本当に止まっているか」を1つのツール(ListAgentsなど)の返り値だけで判断せず、実際のファイル更新時刻など別の手がかりでも裏取りする。ポーリングループ(sleep付きのwhile/until)を自前で書く場合は、親が終了・killされたら子のループも確実に終了する仕組み(タイムアウトや外部からの強制終了)を別途持たせておく。

- **[実装] Claude Code v2.1.288——サブエージェントの「実際に使われたモデル」とagent map表示のズレを修正** — https://code.claude.com/docs/en/changelog
  - **何が起きたか**: 2026-10-02公開のv2.1.288公式changelogに「Fixed the agent map labeling a sub-agent with the session's model instead of the model it actually ran on (e.g. under `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` or an agent's own `model`)」と明記され、サブエージェント一覧(agent map)がセッション本来のモデル名を表示し続け実際に走ったモデルと食い違う表示不具合が修正された。
  - **なぜ注目されているか**: 09-28付ダイジェストで扱った「セキュリティレビュー用サブエージェントがrefusal後にOpus 5.5から4.8へサイレント切り替わり、親セッションの報告は最後までOpus表記のままだった」(#97687)、09-29付の「Dynamic Workflowsがモデルフォールバック中に起動すると全エージェントがフォールバックモデルに固定される」不具合と同じ「検証に実際使われたモデルが申告と食い違う」系統に対し、公式がagent map表示という具体的な表示経路のバグとして認め修正した追跡例。
  - **自分の設計への示唆**: 09-28・09-29付ダイジェストで示唆した「検証役の出力に実際使われたモデルIDを記録・突き合わせる仕組みを自分で持つ」という対策は、v2.1.288以降は公式のagent map表示自体がある程度信頼できるようになった可能性があるが、それでも自分のログに実際のモデルIDを記録する習慣は変えずに続けるのが安全。

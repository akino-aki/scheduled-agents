# 2026-09-24

- **[実装] Agent Teamsでteammateがforeground subagentを起動するとSubagentHandbackが失敗し、レポートがメイン会話へ漏れ出す——v2.1.270→2.1.280のフラグ有効化に伴うregression** — https://github.com/anthropics/claude-code/issues/96225
  - **何が起きたか**: Agent Teams(experimental)を有効にしたauto modeで、in-processなteammateがさらにforeground subagentをspawnすると、subagent側の`SubagentHandback`が「the agent that spawned you is no longer running」で拒否される。teammate自身の`Agent`呼び出しも失敗し、レポートが`<agent-message>`としてメイン会話に漏れ出し、`ListAgents`の階層表示も崩れる。(2026-09-23報告、v2.1.280・macOS、Issue open、regression/has repro)
  - **なぜ注目されているか**: `tengu_lively_waffle`というフィーチャーフラグが2.1.270のデフォルトfalseから2.1.280でtrueに切り替わったことが原因と、コード分析まで添えて特定されている。スポーン元(teammate)の生存性チェックが「待機中のin-process teammateはliveと判定しない」という、親子ハンドオフの契約自体が特定バージョンから崩れた具体例。
  - **自分の設計への示唆**: 出題生成・検証をAgent Teamsのteammate機構で組み、teammateがさらに検証役subagentを起動する階層構成にする設計は、現バージョンのauto modeではレポートが握りつぶされたりメイン会話に漏れたりしうると知っておく。当面はteammateからのさらなるforeground起動を避け、親が直接subagentを起動するフラットな構成にする。

- **[停止条件][実装] 組み込みのfork型subagentに200ターンのハードコード上限——他のsubagentタイプやメインエージェントには無い制限が2026年4月から存在** — https://github.com/anthropics/claude-code/issues/96455
  - **何が起きたか**: `/code-review`などで使われるfork型subagentには、少なくともv2.1.117(2026年4月)から`maxTurns: 200`がハードコードされており、到達すると「stopped at its 200-turn limit」で強制中断される。`general-purpose`など他のsubagentタイプやメインエージェントには同様の上限がない。報告者は、この上限が「200ターン以内に終わらせようと品質を犠牲にする」連鎖的な悪影響も生むと指摘している。(2026-09-23報告、Issue open、enhancement)
  - **なぜ注目されているか**: 09-18付ダイジェストで扱った「デスクトップの`/code-review`がfork subagentの独立性を欠く」#95165とは別角度で、今回はfork型subagentという型そのものに、他のタイプには無い暗黙の上限が存在すると判明した。バイナリ検査で存在が裏付けられており、ドキュメントにも明記されていない。
  - **自分の設計への示唆**: 検証役を`ReportFindings`を使うfork型subagent(code-review系)で組む場合、長時間・野心的な検証タスクは200ターンで問答無用に打ち切られると知っておく。出題の検証パイプラインをfork型で組むなら、1回の検証が200ターン以内に収まる粒度に分割するか、fork以外のsubagent_typeを使う。

- **[実装] Claude Opus 5.5がデフォルトOpusに——キャッシュ読み込み60%値下げ・出力30%高速化で、検証fan-outのコスト構造が直接下がる** — https://www.anthropic.com/claude-opus-5-5
  - **何が起きたか**: 2026-09-22、Claude Opus 5.5(`claude-opus-5-5`)が新しいデフォルトOpusモデルとして公開された。入力$5→$4/Mtok、出力$25→$20/Mtok、キャッシュ読み込み$0.50→$0.20/Mtok(60%減)に値下げされ、公式は「典型的なワークロードでOpus 5より約40%安い」「出力は30%速い」としている。(公式発表、2026-09-22)
  - **なぜ注目されているか**: 09-22付ダイジェストで扱った「3レンズ検証137体超で全滅」(#94911)や「money-audit 547体計画・$606」(#95816)は、いずれもOpusベースの検証fan-outでのコスト暴走だった。同じ長いコンテキスト(finding一覧など)を何度も参照する検証ループは特にキャッシュ読み込みに依存するため、今回の値下げはこの種の構造のコストを直接下げる。
  - **自分の設計への示唆**: 出題検証をOpusベースのfan-outで組む設計は、モデル更新だけで体感コストが下がりうると知っておく。ただし値下げは暴走そのものを防ぐわけではないので、安くなったことを理由に検証レンズ数やラウンド数を増やす判断はせず、finding件数の上限管理はこれまで通り自分で行う。

- **[実践][停止条件] Workflow検証パイプラインが35候補全通過という異常値を機に、verifier段階化・finder統合・サイズ予算でエージェント数を79→44体の見積もりに再設計** — https://github.com/pdcarlson/Frapp/issues/2482
  - **何が起きたか**: モバイルアプリの差分レビューをWorkflowで回したところ、35ファイルに対しfinder+verifierで79エージェント・約5.4Mトークンを消費したのに35候補全てが検証を生き残った。開発者はこれを検証が機能していないサインと判断し、(1)候補ごとのverifierを1つに絞りREFUTEDの時だけ別の観点の2人目を追加、(2)finderの角度を4→2種に統合、(3)`workflowSizeGuideline: "medium"`に統一し25エージェント超で警告、(4)全エージェントに`effort`を明示指定してultracodeのxhigh依存をやめる、という4つのガードレールを設計し、同等のレビューを44エージェントで賄える見積もりを立てた。(2026-09-22投稿、Issue open、PR #2487でレビュー中)
  - **なぜ注目されているか**: 09-22付ダイジェストで扱った「3レンズ検証33件全て不合格」(#94911)は不合格率が異常という角度だったが、今回は逆に全通過(合格率100%)を同じ「検証ロジックが壊れているサイン」として扱い、verifier段階化・finder統合・size budget・effort明示という具体策にまで落とし込んだ、利用者発の実装例である点が新しい。
  - **自分の設計への示唆**: 出題の生成→検証パイプラインで、検証結果が全滅または全通過という極端な値を示したら検証ロジック自体を疑うチェックを自分のパイプラインに入れる。「REFUTED(不合格)の時だけ2人目のverifierを追加起動する」段階化は、出題検証(1次判定→疑わしい問題だけ2次検証)にそのまま転用できる。

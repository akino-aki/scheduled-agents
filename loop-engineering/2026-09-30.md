- **[停止条件] ハーネスがCLIの`max_turns`自己申告を信用した結果、上限75に対し221ターン・予算$4に対し$5.64まで暴走——修正で全バックエンドがAPI呼び出し数を自前カウントする方式に統一** — https://github.com/UiPath/coder_eval/issues/193
  - **何が起きたか**: UiPathのコーディングエージェント評価ハーネスで`max_turns: 75`・`max_usd: 4.0`を設定した試行が、Bedrock経由の一部ルートでClaude Code CLI自身のターンカウンターが発火せず221ターン・$5.64まで暴走。ハーネスは`max_turns`を「ハード上限」と文書化しつつ、実際はCLIの自己申告に依存し独自の歯止めを持っていなかった。(2026-09-22報告、2026-09-23にPR #194でマージ)
  - **なぜ注目されているか**: これまで扱ってきたfan-out予算超過の多くは「見積もりや確認が手前で欠けている」問題だったが、今回は明示的に設定していた上限値自体が、CLI内部カウンターが特定ルートで発火しないだけで3倍近く超過するという、既存の停止条件そのものの脆さを示した。修正PRはClaude Code・OpenCode・Pi・Codex・Antigravity・Delegateの6バックエンドで「1メインスレッドAPI呼び出し=1ターン」に定義を統一し、ハーネス側でAPI呼び出し数を自前カウントしてN+1回目の呼び出し開始時に強制終了する方式にした。
  - **自分の設計への示唆**: 自作routineやskillで反復回数を制限する設計は、CLIやSDKが報告する「ターン数」をそのまま信用せず、自分の呼び出し側で実際のAPI呼び出し回数を数えて独自に打ち切る仕組みを持つ。複数のモデル/経路を使い分ける構成では、報告される回数が経路によって信頼できないことがあると知っておく。

- **[実践] 一晩5セッションの自律ループでPR1件あたり実測$25、コストの43%は「監督セッション」——in-loopレビューが最も費用対効果が高いと判明** — https://github.com/ayushb3/BubblyChef/pull/608
  - **何が起きたか**: GitHub issue→実装→レビュー→マージを回す自律ループを一晩5セッション実行した実測コストレポートによると、合計約$289(Proプランでの API定価換算)で5件のissueを解決・マージし、PR1件あたり約$25。コストの43%はコンテキストサイズに起因する「監督セッション」に費やされており、事前PRレビュー(in-loopレビュー)が最もコスト対効果の高い工程で、別の直接デプロイ方式は費用対効果が低いため不採用と結論した。(2026-09-23公開)
  - **なぜ注目されているか**: これまで扱ってきたコスト記録の多くは「予算を使い切った」「上限が守られなかった」という異常系だったが、今回は正常に完走したループの実測コスト内訳を成果物1件あたりの単価まで含めて公開した、数少ない実践記録である点が新しい。
  - **自分の設計への示唆**: 出題生成→検証→公開のループを毎日routine化する場合、「生成」より「監督(レビュー・調整)」側にコストの半分近くが偏りうると知っておく。事前検証にコストをかける判断が費用対効果で正しいか、軽量な代替(直接公開など)と内訳を比較してから決める。

  - **何が起きたか**: 自律ループのトークン使用量を717件のトランスクリプト・7万124件のAPIリクエストにわたって実測プロファイリングした結果、コスト換算トークンの内訳はキャッシュ読み込みが約76%・5分キャッシュの書き込みが約17%を占め、出力トークンは約3%に過ぎないと判明。ワーカーは1リクエストあたり約30万トークンを再読み込みしており、アイドル時間が5分のキャッシュTTLを超えて発生するサブエージェントのキャッシュ書き込み(約1.9億トークン、総コストの約9%)も無駄として特定された。(2026-09-27報告)

# 2026-10-07

- **[実践][停止条件] server-gated token budgetがsub-agentに10万トークンの予算を課し、予算切れ→自動respawnを数時間繰り返す無限ループ** — https://github.com/anthropics/claude-code/issues/99950
  - **何が起きたか**: v2.1.290で導入されたserver-gated機能が各sub-agentに「開始コンテキスト(system prompt・tools・初期プロンプト)は含まない10万トークン」の予算を課し、予算切れになったsub-agentが「budget exhausted」を報告すると親エージェントが新しいsub-agentを自動再生成、これが数時間繰り返された。同一アカウント内でもFable 5.1のメインセッションだけ有効化されるなど、機能の有効化自体が一貫していなかった。(2026-10-06報告、v2.1.291、Issue open)
  - **なぜ注目されているか**: これまで扱ってきた暴走ループの多くは予算管理の欠落が原因だったが、今回は逆に暴走を防ぐために導入されたばかりの予算管理機能自体が、予算切れを「失敗」として自動的に再試行させる設計のせいで新たな無限ループを生んだという、対策が新しい暴走を生む逆説的な事例。
  - **自分の設計への示唆**: 出題生成・検証のサブエージェントに固定のトークン予算を設け、超過したら自動的に再起動する設計を入れる場合、「予算切れ=即リトライ」ではなく「予算切れが連続したら呼び出し側に報告して停止する」という再試行回数の上限をセットで持たせる。

- **[実践][停止条件] バックグラウンドsubagentが権限プロンプトでブロックされても親セッションに信号が届かず、無人の`/loop`実行が11.5時間無応答で停止** — https://github.com/anthropics/claude-code/issues/99887
  - **何が起きたか**: バックグラウンドのsubagentがローカルHTMLファイル(UIモックアップ)を開こうとして権限プロンプトが発生したが、親セッションには通知も状態表示も届かず、無人で回していた`/loop`によるPRの実装・レビュー作業が深夜1:30〜13:00の11.5時間完全に停止した。親エージェントは「待っているものは何もない」と報告し続け、ユーザーが手動で許可をクリックするまで解消しなかった。(2026-10-06報告、インシデント発生は2026-09-26〜27夜、v2.1.281、Issue open)
  - **なぜ注目されているか**: これまで扱ってきたbackground subagentの通知ロスの多くはwatchdogやハンドバックの実装不具合だったが、今回は権限プロンプトという、無人運転では本来発生させてはいけない種類のブロッキングイベントが、通知経路自体を素通りしてしまうという、より基本的な見落としを示した。
  - **自分の設計への示唆**: 出題生成・検証をバックグラウンドのsubagentに任せる設計では、ファイルを開く・ブラウザを使うなど権限プロンプトを誘発しうる操作をプロンプトで明示的に禁止する(報告者の回避策と同じ)。無人実行の構成では権限を要求しうるツールを最初から使わせない設計にする方が、通知の仕組みを信用するより確実。

- **[停止条件] `/goal`の停止チェックが「ユーザーが指示した引き継ぎ」を認識できず、同じ停止拒否を上限なく約30回連続** — https://github.com/anthropics/claude-code/issues/100075
  - **何が起きたか**: 終了状態だけを書いたgoal(中間の停止可能点を含まない)に対し、ユーザーが「ここで打ち切って次セッションへの引き継ぎファイルを書き、新しい作業は始めないで」と明示的に指示しても、`/goal`の停止チェックはgoal本文とセッション履歴だけを見て「まだ終わっていない」と判定し続け、同じ停止拒否を約30回連続で繰り返した。ユーザーは手動で`/goal clear`を打つしかなく、保持したかったgoal自体も失われた。(2026-10-06報告、v2.1.290前後、Issue open)
  - **なぜ注目されているか**: 構造化された終了理由(目的達成・進捗なし・上限到達・人の判断待ちなど)を整理する提案が別途出ている一方、Claude Code公式の`/goal`機能自体にはまだ「ユーザーが明示的に指示した一時停止」を終了理由の一種として区別する仕組みも、拒否回数の上限も無かったという具体例を示した。
  - **自分の設計への示唆**: 自作のgoal/loop型routineで終了判定を「目標文とログだけを見て判定する」設計にしている場合、ユーザー(自分)が明示的に打ち切りを指示した時だけは別チャネルとして扱い、通常の停止判定ロジックをバイパスできるようにする。「同じ停止拒否がN回続いたら自動的に止めて報告する」という拒否回数の上限も、goal系ループで自分で実装しておく必要がある。

- **[実装][停止条件] Claude Code v2.1.290——会話がcompactされた後に`/loop`のスケジュールされたタスクが静かに戻らなくなる不具合を修正** — https://code.claude.com/docs/en/changelog
  - **何が起きたか**: 2026-10-05公開のv2.1.290公式changelogに「Fixed scheduled tasks (`/loop` with an interval, reminders) silently not coming back on resume once the conversation was compacted」と明記。間隔指定の`/loop`やリマインダーが、会話がcompact(要約)された後にresumeしても、予定されていたはずの次回起動が静かに失われ二度と戻ってこなかった不具合が修正された(この修正以降に行われたcompactionにのみ適用)。
  - **なぜ注目されているか**: これまで扱ってきた停止条件の壊れ方の多くは「止まるべき時に止まらない」系統だったが、今回は逆に長時間routineの土台である`/loop`自身の再起動メカニズムが、長く動かせばほぼ必ず発生するcompactionという普通の出来事だけで静かに失われるという、日次routineのような長期運用で特に刺さる不具合を公式が認めて修正した。
  - **自分の設計への示唆**: このダイジェストroutine自体も含め、長時間・多数ターンにわたる`/loop`運用ではcompaction後にスケジュールが本当に戻っているかを信用せず、v2.1.290以降への更新を確認する。それでも「次回起動が来なかったらどう検知するか」という外部からの生存確認(例えば前回のpush時刻をチェックする等)は別途持っておくと安全。

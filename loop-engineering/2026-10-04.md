- **[実践][停止条件] 600秒のbackground wait ceilingがメインスレッド基準で計測され、強制killされたサブエージェントが「ユーザー拒否」兼exit 0の成功として記録される** — https://github.com/anthropics/claude-code/issues/98170
  - **何が起きたか**: `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS`(既定600秒)がバックグラウンドタスク自身の最終活動ではなくメインスレッドの最後のメッセージ時刻から計測されるため、pytest等まだ進行中の処理が打ち切られる。2026-09-28の実例では11エージェント・2時間32分・$110.03のワークツリー実行が`killed.system:9`で強制終了されたにもかかわらずresultは`success`・exit 0で返り、ログには"User rejected tool use"と記録された。(2026-09-29報告、v2.1.284、Issue open)
  - **なぜ注目されているか**: background subagentの通知ロス系統の中でも、今回は「止められた」という事実自体がログから消え、ユーザー拒否・成功という正反対の意味のステータスに書き換わってしまう点が新しい。呼び出し側がresultを信用すると、未完了の作業を完了済みとして扱ってしまう。
  - **自分の設計への示唆**: background subagentを使うなら、result の success/exit 0 だけでなく `subagent_stats` 内の `killed.system` のような内部フィールドも必ず確認する。タイムアウトはメインスレッドの最後の発言から計測される前提で、検証ループのサブエージェントには十分なマージンを持たせるか、自前で進捗をポーリングする仕組みを入れる。

- **[実践][停止条件] 7並列fan-outのうち大きいコンテキストを持つ1体だけが20%の確率で600秒まるごと沈黙——event-level watchdogも効かない** — https://github.com/anthropics/claude-code/issues/98236
  - **何が起きたか**: Vertex AI上のClaude Code v2.1.284で、7体並列起動のうち毎回同じ役割の大規模コンテキストサブエージェント(約25ファイル・14万トークン超読み込み)だけが83回中17回(20%)、ツール呼び出し0・トークン消費0のまま600秒ちょうど沈黙して終了。同バッチの他6体は200回中0件。ドキュメント上は300秒のevent-level watchdogがあるはずだが機能していない。(2026-09-29報告、Issue open、5週間分のテレメトリ提供可能)
  - **なぜ注目されているか**: 停止条件を監視するはずのwatchdog自体が、コンテキストが大きい役割・特定プラットフォームという条件下では発火しないまま沈黙だけが続くという、監視機構の盲点を具体的な発生率付きで示した。
  - **自分の設計への示唆**: 出題生成を並列fan-outで組む場合、コンテキストが大きい役割のサブエージェントだけ特定の環境で沈黙率が上がる可能性があると知っておく。watchdogの作動を信用せず、呼び出し側でも「開始から○秒応答が無ければ再試行」という独立のタイムアウトを持たせる。

- **[実装][停止条件] Claude Code v2.1.288——無人セッションの自動リトライが「3回タイムアウトしたら諦める」方式に変更、バックグラウンドコマンドの時間制限も無人セッション限定に** — https://code.claude.com/docs/en/changelog
  - **何が起きたか**: 2026-10-02公開のv2.1.288公式changelogに「Fixed unattended sessions (`CLAUDE_CODE_RETRY_WATCHDOG`) retrying for hours after a very long response stream failed; Claude Code now streams again, and gives up after three timeouts」と明記。同リリースでバックグラウンドコマンドの時間制限(既定30分・最大2時間)も、`-p`/Agent SDK/CI/cloud等の無人セッションのみに適用し、ターミナル・デスクトップアプリ・VS Codeセッションには制限を設けない形に変更された。
  - **なぜ注目されているか**: これまでの自己リスケジュール型ループの暴走報告は「回数上限が無い」ことが原因の中心だったが、今回は逆に公式が無人セッションの自動リトライへ回数上限(3回)を新規に加え、同じ「時間制限」という概念を無人セッションか対話型セッションかで明示的に切り分けた点が新しい。
  - **自分の設計への示唆**: routineやCI経由で動く無人セッションは今後3回タイムアウトすると自動的に諦める挙動になると知っておき、生成→検証ループの各ステップがその範囲内で完了する設計にする。対話型(ターミナル/デスクトップ)セッションでバックグラウンドコマンドを使う検証は時間制限が無くなる分、自分で上限を決めて監視する必要がある。

- **[実装][停止条件] OpenCodeの「未完了Todoがあれば停止させない」継続ガードをClaude CodeのStop hookへ移植——セッションあたり最大2回までの打ち切り付きで** — https://github.com/marcusquinn/aidevops/issues/33143
  - **何が起きたか**: OpenCodeのsession-continuation-guardは、トランスクリプト中に未完了(pending/in_progress)のTodoItemが残っており、かつ最終メッセージが明示的な完了宣言やブロッカー報告でない場合にセッションの停止をブロックする仕組み。aidevopsはこれと同等の挙動をClaude CodeのStop hookとして実装し、セッションごとに最大2回までブロックしたら以降は停止を許可、ヘッドレスセッションやユーザーの明示的な停止要求では制限しない設計にした。(2026-09-30提起、PR #33215でクローズ)
  - **なぜ注目されているか**: 他ツール(OpenCode)の停止条件設計をClaude CodeのStop hookへ移植する際、「無制限に粘らせる」のではなく「2回まで」という上限とヘッドレス除外を最初からセットで組み込んだ点が新しい。継続ガード自体が別の暴走の火種にならないよう設計された具体例。
  - **自分の設計への示唆**: 自作のStop hookで「todoが残っていたら停止させない」設計を入れる場合、無制限に粘らせず最大リトライ回数(例:2回)を最初から組み込む。ヘッドレス/自動実行のセッションではこのガードを無効化しておき、人が見ていない場での無限粘着を避ける。

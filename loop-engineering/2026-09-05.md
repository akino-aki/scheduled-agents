  - **何が起きたか**: ユーザーは`/ultracode`を一度も有効化していないのに、システムリマインダーが「Ultracode is on」と誤表示し、モデルがそれを事実として2本のWorkflow(56体・104体、計160体)を自動起動。約12分で計約320万サブエージェントトークンを消費して5時間のセッション上限を使い切り、160体中約92体がセッション上限エラーで失敗した。次のターンでは同じリマインダーが「Ultracode is off」に戻っていた。(2026-09-03 21時頃発生・09-04報告、claude-fable-5-1・Linux、Issue open)
  - **なぜ注目されているか**: 09-04付ダイジェストで扱った「finder×refuter型レビューが式の乗数構成で15体ガイドラインをすり抜け100体超に膨張」#91845は"式が青天井だった"という設計側の穴だったが、今回はガイドラインをすり抜ける以前に「マルチエージェントモードが有効かどうか」というシステム状態そのものが虚偽表示され、ユーザーの明示的な事前指示(「Workflowは明示要求時のみ使う」)すら無視された点が新しい。
  - **自分の設計への示唆**: 出題生成・検証のWorkflowをultracode等のマルチエージェントモードに頼る設計は、モード表示を過信せず、実際に起動されたWorkflow runの数を実行ログで都度確認する。「明示要求時のみ」という運用ルールはCLAUDE.mdに書くだけでなく、hookでWorkflow呼び出し自体を許可制にすることも検討する。

  - **何が起きたか**: 同じ「research」ステップをclaude-fable-5に書かせると6〜7体のサブエージェントに収まるのに対し、claude-fable-5-1に自己作成のWorkflowスクリプトを書かせると19〜25体を割り当て、Workflowツールの「15体以下」既定ガイドラインを超過した。約7体構成なら約400万トークンで済むところ19〜25体構成では約7,880万(実効)トークンを消費し同等タスクの約3倍のコストとなり、一部はセッション上限エラーで失敗した。(2026-09-02報告、Issue open)

- **[実装][停止条件] Claude Code v2.1.260/v2.1.261 — 別エージェントからSendMessageで再開されたサブエージェントが完了時に起こされない不具合と、Workflowのサブエージェントがcompaction中に「stalled」と誤判定されリスタートされる不具合を修正** — https://code.claude.com/docs/en/changelog
  - **何が起きたか**: v2.1.260(2026-09-03公開)で、あるサブエージェントが別のエージェントからSendMessageで再開された場合に完了通知が再開元ではなくメイン会話に届き起こされない不具合、長時間のコンテキストcompaction中にWorkflowツールのサブエージェントが誤って「stalled」とみなされリスタートされる不具合、agent teamsの長いAPIリトライ待機中にチームメイトのトランスクリプトが欠落・空白化する不具合を修正。翌v2.1.261(2026-09-04公開)では、バックグラウンドでWorkflow/エージェントがまだ実行中なのにターミナルの進捗表示が「セッション終了」と誤表示する不具合も修正された。
  - **なぜ注目されているか**: 09-02〜09-04付ダイジェストで扱ってきた「SendMessageの返信がルートへ誤配信される」#91242・#90463系統、「Workflowの稼働中が外部から見えない」#90034系統に、公式が2バージョン連続で手を入れた。特にcompaction中の誤リスタートは、長時間動くサブエージェントほど遭遇しやすく、これまで扱った「利用上限到達時の全損」#91449とは別の再実行トリガーとして具体的に塞がれた。
  - **自分の設計への示唆**: 出題生成・検証をSendMessageでの多階層サブエージェント連携やWorkflowの長時間サブエージェントで組む設計は、v2.1.260/261以降ならこの2つの誤リスタート・誤配信経路は塞がれていると見込める。ただし「進捗表示が終了と誤表示する」系統の不具合はこれまでも別経路で繰り返し出ているため、表示を信じず実行ログでの確認を引き続き習慣にする。

- **[実践][停止条件] ドキュメント上は稼働中のサブエージェントへ`SendMessage`で修正を送れるはずが実ビルドにはそのツールが存在せず——8分かけて設計した内容を、2分後に撤回された制約のまま最後まで書き上げ破棄する羽目に** — https://github.com/anthropics/claude-code/issues/92134
  - **何が起きたか**: `ListAgents`や`Agent`ツールの説明文は稼働中のサブエージェントへ`SendMessage`で追加指示や訂正を送れると案内しているが、実ビルドには該当ツールが存在せず`ToolSearch`で検索してもヒットしない。唯一近い名前の`mcp__ccd_session_mgmt__send_message`はセッション間通信専用で自セッションを宛先として拒否するため代替にならない。実例では`Plan`サブエージェントがWindowsサービス再起動機構の設計に8分以上費やした2分後にその制約自体が撤回されたが、訂正を伝える手段が無く該当部分をまるごと破棄する結果になった。(2026-09-04報告、v2.1.210・Windows・Opus 5、Issue open)
  - **なぜ注目されているか**: ドキュメント(ツール説明文)が保証する機能が実ビルドに存在しないという、配送経路の不具合とは別カテゴリの指摘。09-02付ダイジェストで扱った「サブエージェントへのSendMessageが期待チャネルに届かない」#91242は届いた後の誤配信だったが、今回は呼び出し自体がそもそも失敗するという、より手前の欠落。
  - **自分の設計への示唆**: 検証AIが不合格を出したときにサブエージェントへ即座にフィードバックして継続させる設計は、SendMessageでの介入自体がビルドやバージョンによって使えない場合があると知っておく。介入できない前提に立ち、「訂正が必要になったら現在のサブエージェントは打ち切って新しいプロンプトで再起動する」という、通信よりリスタート前提のフォールバックを組み込んでおく。

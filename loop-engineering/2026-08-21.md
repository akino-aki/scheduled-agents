- **[実践][停止条件] ScheduleWakeupが`/loop`外でも自発的に呼ばれ`prompt`欠落で検証エラーが漏れる——バックグラウンド分業待ちの場面で16セッション以上・複数週にわたり再現** — https://github.com/anthropics/claude-code/issues/88260
  - **何が起きたか**: plainセッション(`/loop`外)でバックグラウンドサブエージェントの完了を待っている場面で、Claudeが自発的に`ScheduleWakeup`を呼ぶが必須の`prompt`フィールドを省略し、生のバリデーションエラーがそのままtranscriptに漏れる。ツール自身の説明文が「ポーリングは無駄」と明記しているにもかかわらず、16以上の独立セッション・複数週にわたり同一パターンで再現(次ターンで自己修正はする)。（2026-08-20報告、v2.1.237、Issue open）
  - **なぜ注目されているか**: 8/16・8/17付ダイジェストの「サブエージェントの完了通知が遅延/検知できない」系統とは逆に、今回はモデル自身が「投げっぱなしで待てない」不安から、明示的に禁止されたポーリングへ手を伸ばしてしまう傾向が定量的に確認された。
  - **自分の設計への示唆**: バックグラウンドサブエージェントの完了を待つ設計では、モデルが自発的にポーリング相当の動作を試みてエラーだけ出すことがあると織り込む。エラー自体は自己修正されるため実害は薄いが、transcriptに生のエラーが出ても異常と早合点しない。

- **[実践][停止条件] `claude -p`が未知のスラッシュコマンドでも終了コード0を返す——プラグインコマンド回帰で無人パイプラインが11時間気づかれず失敗し続けた実例付きで是正要望** — https://github.com/anthropics/claude-code/issues/88387
  - **何が起きたか**: `-p`(print)モードで存在しないスラッシュコマンドを実行してもエラーはstdoutに出るだけで終了コードは0(成功)のまま。実際に2026年7月、v2.1.205のプラグインコマンド回帰(#76066)で`/structured-workflows:help`等のプラグインコマンドが軒並み「Unknown command」になったにもかかわらず終了コード0のため検知されず、一晩(約11時間)分の自動化パイプラインが空の結果を積み上げ続けた実例が引用されている。終了コードを非ゼロにしメッセージをstderrへ出すよう要望。（2026-08-20報告、v2.1.238、Issue open）
  - **なぜ注目されているか**: 8/19付ダイジェストの「headlessセッションが429/5xxで即致命的終了する」#87692とは逆方向で、今回は本来失敗を示すべき場面が成功扱いになり検知できない失敗。無人ヘッドレス運用の核心である「失敗したら気づける」という前提が、終了コードという最も基本的なシグナルの設計ミスで崩れていたと、11時間分の実被害付きで示された。
  - **自分の設計への示唆**: 出題生成・検証を`-p`ヘッドレス実行で無人化するなら、終了コード0を成功の証拠として信用せず、stdoutの中身(コマンド名の妥当性やエラー文言)も自前でパースして異常を検知する層を挟む。プラグインコマンドをheadlessパイプラインの起点に使うのは特にこの回帰の再発リスクを意識する。

- **[実装][停止条件] Claude Code v2.1.238 — 長時間対話セッションでのメモリ無制限増大を修正、サブエージェントのツール結果を表示ウィンドウ外で解放** — https://github.com/anthropics/claude-code/releases/tag/v2.1.238
  - **何が起きたか**: v2.1.238(2026-08-20公開)で、長時間の対話セッションにおけるメモリの無制限な増大を修正。サブエージェントのツール結果は、直近の表示ウィンドウから外れた時点でメモリから解放されるようになった。同リリースではクロスセッションメッセージングで、受信拒否設定のセッションやレート制限/キュー満杯で届かなかったメッセージが「送信成功」と誤表示されず送信元に通知される修正も入った。
  - **なぜ注目されているか**: これまでのダイジェストで扱ってきた暴走防止は主に時間(watchdog)やCPU/メモリ上限(cgroup、8/15付v2.1.233)など「外側から強制終了する」方向の対策だったが、今回は逆にツール自体のメモリ効率を上げて長時間セッションの土台を底上げする修正で、サブエージェント分業を多用するほど蓄積していたはずの問題への直接対処。
  - **自分の設計への示唆**: worktree並列やサブエージェント分業で長時間loopを回す設計では、このバージョン以降ならメモリ増大が緩和されている前提を持てる。旧バージョン運用中でセッションが重くなっていた場合は、この修正が原因だった可能性を疑い更新を検討する。

- **[実践][停止条件] Haiku 5の週間レート制限到達でセッション全体が終了——Opus 5へのフォールバックが働かず進行中の複数ワークフローを喪失** — https://github.com/anthropics/claude-code/issues/88390
  - **何が起きたか**: Haiku 5の週間レート制限に到達した際、他の利用可能なモデル(Opus 5)へ自動フォールバックするはずの挙動が働かず、セッション自体が終了してログアウトされた。進行中だった複数ワークフローを含む長期セッションが失われ、`VirtualMessageList: itemKeys/messages length desync`という内部エラーを伴っていた。（2026-08-20報告、v2.1.233、Windows、Issue open）
  - **なぜ注目されているか**: 8/18付ダイジェストの「モデル階層を使い分けてもUsageレポートが誤帰属する」#87446と同じく複数モデル運用の穴だが、今回はコスト表示の誤りではなく、セッションの生存そのものがモデル切り替え失敗に巻き込まれて終わるという、より直接的な実害。
  - **自分の設計への示唆**: 検証AIに安価なモデルを明示指定する設計(8/17付の教訓)を使うなら、そのモデル単体のレート制限で長時間セッション全体が落ちるリスクを織り込む。無人routineで複数モデルを使い分けるときは、レート制限到達時にセッションが生き残るかを一度確認しておく。
